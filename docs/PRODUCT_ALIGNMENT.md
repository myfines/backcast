# 产品对齐：让 AI 替用户查知乎答主的历史发言

对齐日期：2026-11-16。以下取舍来自用户逐项回答，优先于早期全领域原型与原型的演示数据。

## 用户要解决的问题

用户看到某位知乎答主的说法，想知道这个人在相关领域是否值得相信，却没有时间逐条翻历史、找外部事实、核对过去的预测。Backcast 接受自然语言需求及知乎答主标识，自动执行这段调查。

主入口：**输入知乎答主 / 主页链接，说明想判断什么**。
次入口：输入领域或问题，寻找值得参考的答主和回答。
目标用户首先是核查现有大 V / 答主的人。专家推荐来自这些历史调查记录，而非预先制作一个专家榜单。

## 已确认的优先级

- 平台只做知乎；结果核验证据允许来自外部公开资料。
- 事实准确性、论证依据优先，预测兑现情况其次；两种表现分开评价。
- 用户不希望推荐那些知识很多、但趋势预测经常出错的人。不能用大量容易的事实命中掩盖关键预测错误。
- 合订本以“当时的判断—后来发生的事实”的对照为核心。
- 用户希望系统给出有依据的直接建议，也能自己点开原话和证据核对。
- 用户输入想要什么，采集、提取、检索、核查、报告应自动执行；人工复核是纠错路径，不是主流程的必经步骤。
- 用户暂无指定答主或案例。候选领域可选消费科技、AI 工具、天文科普等，案例要先核查，避免国内敏感争议及 BTC 展示。
- 路演希望证明：系统能区分哪些言论缺乏事实支撑、哪些判断确实有效。

## 推荐的主流程

1. 用户提交答主主页 / 唯一标识及自然语言目的，例如“看看他过去关于 AI 工具的判断是否值得参考”。同名作者必须辨明身份，不默认搜索第一名就是目标。
2. 自动检索可取得的公开回答与文章，保留题目、原文位置、作者标识、来源链接、发表/编辑时间和检索时间。
3. 按时间及话题形成披露范围的样本；提取论证中的关键事实与可检验预测，避免只数无关紧要的常识。
4. 固定检验口径后查找外部支持与反证，核对引用是否实际存在、是否支持结论、时间是否匹配。
5. 给出人物报告：一句直接结论、事实记录、预测记录、代表性正反案例、不确定项与覆盖边界。
6. 从已有核查结果中，推荐同类问题下更值得参考的人与具体回答。证据不足时直接说无法建议，不生成虚构分数。

## 报告与示范

用户首先看到“已核查的记录是否足以支持参考这个人的判断”，随后能打开支撑建议的原话与证据。建议应限于具体领域及已获得样本；不推测个人动机或诚信。

路演优先展示一次真实人物调查：输入目标 → 显示实际检索进度与覆盖 → 查看关键事实/预测的核验 → 给出参考建议 → 展开证据。样本数、命中数及人物优劣都必须来自真实运行结果，不能为了戏剧性凑反例。

此前五条人工种子案例与 Brier 面板只能说明基础程序可运行，不代表已完成此主流程。用户历史采集、事实陈述评分和人物级自动报告仍是实际产品缺口。

## 与现有代码的衔接

- 保留导入记录、证据、时间门槛、审计与 provider 接口。
- 把任务入口提升为人物级研究，文章级命题核验作为子任务。
- 为事实陈述单独建立时间匹配的核验统计；不能仅沿用预测的版本资格门槛或把预测概率评分作为通用可信度。
- 概率统计保留为适用场景下的工具，不要求知乎答主用百分数表述才有可分析的记录。
- 优先确认知乎官方/赛事接口的数据边界，并为可公开检索的历史内容实现覆盖报告。不要先宣称任意人物的全历史已经能拿到。

## 赛事

截至本次研究，官方最近展示的是[知乎黑客松 S3 · 湾区共创季](https://hackathon-s3.event.zhihu.com/)。官方提供技术指南及 Skill 入口，但本次没有取得受登录保护的技术指南，也没有实测赛事权限。

公开 CLI 0.2.0 随附[接口文档第9节](https://docs.rs/crate/zhihu-cli/0.2.0/source/docs/api-reference.md)明确：用户数据默认本人，其他用户需目标用户 OAuth 授权。该接口不能直接当作任意答主全历史读取接口；赛事额外能力须另行核实。
